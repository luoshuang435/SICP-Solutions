原有的 good-enough? 测试是判断 guess 的平方和 x 的绝对差是否小于一个固定阈值（如 0.001）。

```scheme
(define (good-enough? guess x)
  (< (abs (- (square guess) x)) 0.001))
```
这个固定阈值的测试方式，在处理非常小或非常大的数时会失效。

- 失效1：对于非常大的数，测试过于严格（甚至导致死循环）  
对于极大的数，两次相邻的浮点数之间的“间隙”会变得很大。当牛顿迭代法improve对猜测值guess的改进小到无法用下一个浮点数表示时，(improve guess x)就会返回和guess相同的值。如果此时(- (square guess) x)的差值仍大于0.001，程序就会陷入死循环。
  
  这是一个很有意思的练习，因为它迫使我们去探究计算机“幕后”如何处理某些类型的数字。更具体地说，是探究计算机如何使用“浮点”格式对实数进行编码。
  
  与整数格式相比，使用浮点格式存储数字的优势在于它可以表示更广泛的数值范围，从极小到极大。在我用于运行测试的 DrRacket 中，它使用 双精度浮点格式，以 64 位存储数字。它允许 15 到 17 位有效数字的精度，这意味着它可以存储和计算像 999,999,999,999,999.9 和 0.000000000000001 这样的数字。这是一个非常宽泛的范围，但该系统也存在一些需要注意的限制：
  - 因为每个数字都编码在有限数量的比特上（在本例中为 64 位），所以计算机可以表示的浮点数数量是有限的。
  - 大多数情况下，浮点数是对实数的近似值。计算过程中，结果会四舍五入到最接近的浮点数。
  - 随着表示数字的位数增加，两个相邻数字之间的“间隔”也会增大。直观地说，整数部分（小数点前）使用的小数位数越多，小数部分（小数点后）可用的数字就越少。
    
  为了了解发生了什么，我们可以逐步跟踪程序的运行过程(sqrt 12345678901234)。我们注意到，在第 26 次迭代之后(improve guess x)，程序返回的值与初始值相同guess，似乎无法再改进结果。

  | 迭代 | guess | (improve guess x) |
  | ------ | ------: | ------: |
  | 0 | 1.00000 | 6172839450617.5000 |
  | 1 | 6172839450617.5000 | 3086419725309.7500 |
  | 2 | 3086419725309.7500 | 1543209862656.8750 |
  | 3 | 1543209862656.8750 | 771604931332.43750 |
  | ... | ... | ... |
  | 22 | 4224503.31128 | 3573450.52229 |
  | 23 | 3573450.52229 | 3514142.33663 |
  | 24 | 3514142.33663 | 3513641.86446 |
  | 25 | 3513641.86446 | 3513641.82882 |
  | 26 | 3513641.82882 | 3513641.82882 |
  | 27 | 3513641.82882 | 3513641.82882 |

  我们还注意到，程序收敛到的最佳猜测值无法满足当前的实现good-enough?。因为(- (square 3513641.82882) 12345678901234) = 0.1313 > 0.001，程序会卡在一个guess不足以满足退出条件的值上，从而形成无限循环。
  
  要了解为什么(improve guess x)无法提供更好的结果，我们需要深入了解计算机中浮点数的实际表示方式，并逐步执行(improve 3513641.8288200637 12345678901234)以查看发生了什么。

  ```bash
  (define (improve guess x)
  (average guess (/ x guess)))
  ```
  ```scheme
  x           = 12345678901234
  guess       = 3513641.8288200637
  (\ x guess) = 3513641.8288200633
  ```
  
  这两个数字非常接近。那么计算如下(average 3513641.8288200637 3513641.8288200633)：
  
  ```bash
  (define (average x y) 
  (/ (+ x y) 2))
  ```
  ```scheme
  (+ x y)        = 7027283.6576401274
  (/ (+ x y) 2)) = 3513641.8288200637 ; same as guess
  ```
  通过使用像[IEEE-754 浮点数转换器](https://numeral-systems.com/ieee-754-converter/)这样的工具 ，可以查看计算机内存中实际存储的 64 位数字的编码方式：
  ```scheme
                S Exponent    Mantissa
  guess       = 0 10000010100 1010110011101001010011101010000101101100011010011110 (3513641.8288200637)
  (\ x guess) = 0 10000010100 1010110011101001010011101010000101101100011010011101 (3513641.8288200633)
  ```
  有趣的是，这两个数不仅非常接近，而且它们的二进制浮点表示也几乎相同。只有最后两位数字不同：这两个数实际上是连续的！这意味着这两个数之间没有其他浮点数，我们已经“达到精度极限”了。
  
  由于improve计算的是guess 和 (/ x guess)的平均值，计算机将把这两个数相加并除以 2，但由于无法表示这两个数之间的浮点数，结果将被四舍五入到最接近的浮点数，即，这就解释了为什么无法产生更好的结果。
  
  既然我们已经理解了为什么猜测无法更准确，接下来我们可以看看为什么good-enough?在这种情况下会返回 false。当我们为两个连续浮点数 guess 和 (\ x guess) 计算good-enough?时，会发现：
  ```scheme
  (square guess)       = 12345678901234.00178
  (square (\ x guess)) = 12345678901233.99800

  (abs (- (square guess) x))       = 0.00178 ; > 0.001
  (abs (- (square (\ x guess)) x)) = 0.002 ; > 0.001
  ```
  因为精度已经达到极限，而且使用的是极大数，所以(- (square guess) x))不能小于某个值0.001，从而导致无限循环。
  
  一个 64 位浮点数的“有效十进制数精度为 15 到 17 位”。由于“12345678901234”有 14 位有效十进制数，“0.001”有 3 位有效十进制数，而 14 + 3 = 17，我们就能理解问题所在了。我们需要的是一个非常大的数字的非常精确的解。这里，就像小数字的问题一样，关键在于所需的精度是绝对的，而不是相对于数字大小的相对精度。
  
  如果运气好的话，guess会收敛到一个固定点，在该固定点上，(- (square guess) x)四舍五入的结果正好等于0.0，计算停止。
  
  如果我们运气不好，两个连续浮点数之间的差值大于0.001，则good-enough?永远不会为真。
  
  提高精度反而0.00000001会使情况变得更糟，因为它会导致 x 的值更小时出现问题。

- 失效2：对于非常小的数，测试过于宽松   
观察(sqrt 0.00000000123)的轨迹，我们发现计算似乎过早停止了：

  | 迭代 | guess | (improve guess x) | (- (square guess) x) |
  | ------ | ------ | ------: | ------: |
  | 0 | 1.000000 | 0.500000 | 1.000000 |
  | 1 | 0.500000 | 0.250000 | 0.250000 |
  | 2 | 0.250000 | 0.125000 | 0.062500 |
  | 3 | 0.125000 | 0.062500 | 0.015625 |
  | 4 | 0.062500 | 0.031250 | 0.003906 |
  | 5 | 0.031250 | 0.015625 | 0.000977 |

  当目标数 x 本身很小（如0.00000000123）时，guess 在迭代中很容易就达到一个平方值小于 0.001 的数。此时，(abs (- (square guess) x)) 会小于 0.001，测试通过，但得到的猜测值 guess 可能离真正的平方根差了几个数量级。如果将误差值0.001变少，计算结果会精确些，但对于更少的数字，精度还是不够。
